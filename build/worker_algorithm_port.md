## Part A. 대책이 경로에 반영되도록 (effects 전달)

### 수정 내용

`fourd_workers` 가 `soft_route(grid, ..., None)` 로 호출하던 것을
`soft_route(grid, ..., path_eff)` 로 바꾸고, `_get_context(grid, path_eff)` 도 같이 맞췄다.
`path_effects_for_day()` 가 그날 그 층에서 **활성인**(=`day >= effective_day`) 대책의
경로 가중 배율을 2D `effects` 어휘로 옮긴다.

### 채널 → 2D 셀타입 매핑

`movement._build_context` 가 `weight_mult` 를 쓰는 자리는 두 곳뿐이다:

```
edge_base = C.OPEN_EDGE_PEN * wm(FLOOR_OPENING)      # 개구부 인접 가산
extra     = HAZARD_WEIGHT[ncell] * RISK_K * wm(ncell)
```

`C.HAZARD_WEIGHT = {MATERIAL: 3.0, NARROW: 2.0}` 이므로:

| 4D 채널 | 2D 셀타입 | 경로 영향 |
|---|---|---|
| `fall` | `FLOOR_OPENING` | **있음** (`OPEN_EDGE_PEN` 경유) |
| `material` | `MATERIAL` | **있음** |
| `narrow` | `NARROW` | **있음** |
| `edge` | `EDGE` | **없음** — `HAZARD_WEIGHT` 에 항목이 없어 0×x=0 |
| `collapse_zone` | (대응 없음) | 없음 — 셀타입 오버레이가 없다 |
| `drop_zone` | (대응 없음) | 없음 — 〃 |

대응이 없는 3채널은 `weight_mult=1.0`(영향 없음)으로 두었다.

### 값을 지어내지 않은 지점 — 이것이 Part A 의 핵심 결과

경로 비용에 쓸 수 있는 값은 규칙의 **`hazardWeightMultiplier`** 뿐이다.
`fallProbMultiplier`(λ 확률 배율)를 경로 가중으로 쓰면 **값의 의미를 바꾸는 것**이므로
하지 않았다.

라이브러리 전수 조사 결과:

| 항목 | 결과 |
|---|---|
| `hazardWeightMultiplier` 를 가진 규칙 | **1건** — `RULE_HS_DEBRISNET` (`ALT_T_HS_02`) |
| 그 규칙의 `appliesToCellType` | `drop_zone` → **2D 셀타입 대응 없음** |
| [S] 10건 중 경로에 영향을 줄 수 있는 scale 규칙 | **0건** |

즉 **현재 라이브러리로는 effects 전달이 경로를 바꾸지 못한다.**
`ALT_H001_05`(개구부 난간)에도 `hazardWeightMultiplier` 가 없다.

### A-2 위험보상행동 — 관측할 수 없다

지시서가 상정한 상충(`weight_mult` 감소 → 회피 약화 → 노출 증가 vs
`prob_mult` 0.10 → 위험 감소)은 **`weight_mult` 가 라이브러리에 없어 발생하지 않는다.**
노출은 변하지 않고 λ 만 줄어든다.

실측 (같은 시드로 BASE 와 짝지어 비교, 전체 공기):

| 대안 | 성격 | 노출 변화 | λ 변화 | 궤적이 BASE 와 동일? | 경로effects 적용일 |
|---|---|---|---|---|---|
| `ALT_H001_05` (개구부 난간) | 계수 | **+0.00%** | **−17.10%** | **예** | 0 |
| `ALT_S_CP_04` (양중 제한) | 계수 | **+0.00%** | −0.80% | **예** | 0 |
| `ALT_T_CP_03` (하부 무출입) | 형상(block) | −11.00% | −6.38% | 아니오 | 0 |
| `ALT_H001_01` (개구부 통합) | 형상(remove) | −8.10% | −16.42% | 아니오 | 0 |

**계수형은 노출이 정확히 0.00% 변한다** — 작업자가 BASE 와 비트 단위로 같은 경로를
걷고 λ 에만 배율이 곱해진다는 뜻이다. 위험보상은 일어나지 않는다.

형상형(remove/block)은 격자가 바뀌므로 **effects 전달 이전에도** 궤적이 달랐다
(`경로effects 적용일 = 0` 인데도 `궤적동일 = 아니오`).

**관측하려면 다음 중 하나가 필요하다(이번에 하지 않음):**
1. 라이브러리에 `hazardWeightMultiplier` 를 **근거와 함께** 추가한다.
   난간이 회피를 얼마나 약화시키는지는 문헌값이 필요하다 — 임의값을 넣으면
   위험보상 효과의 크기를 지어내는 것이 된다.
2. 또는 "방호된 개구부는 회피 대상이 아니다"를 **형상**으로 표현한다
   (예: 난간 설치 후 `OPEN_EDGE_PEN` 대상에서 제외). 이는 계수가 아니라 규칙이므로
   지어내는 값이 없다. **다만 이것도 새 모델링 결정이라 별도 정당화가 필요하다.**

### 경로가 이미 바뀌고 있던 것

`remove`·`block` 은 격자 자체를 바꾸므로 **effects 전달 이전에도** 경로가 달랐다.
`TemporalRule` 도 생멸 일자가 바뀌어 그날 격자가 달라진다.
즉 [S] 10건 중 6건(형상·시점형)은 원래부터 궤적이 달랐고, 4건(계수형)만
λ 배율로만 작용한다.

### 실행 시간 — 우려한 캐시 무효화는 일어나지 않는다

`_get_context` 의 캐시 키가 `id(grid)` 이고 `effects is` 동일성까지 보므로
effects 를 넘기면 매일 무효화될 것을 우려했다. 그러나 **4D 는 (일자, 층)마다 격자를
새로 만들고 끝나면 `movement._CTX.pop(id(grid))` 로 지운다.** 컨텍스트는 원래부터
매번 재생성되므로 effects 를 넘겨도 추가 비용이 없다.

실측 (전체 공기 350일, 1회):

| 단계 | 초/회 |
|---|---|
| stage6 | 16.6 |
| stage7a (+effects) | 12.9 |
| stage7b (+체류) | 11.1 |
| stage7c (+변동) | 11.0 |

### 측정 오염을 하나 잡았다 — 커널이 아니라 대조 스크립트 문제

첫 대조에서 stage7c 가 **2,348초/회**(stage7b 대비 68배)로 나왔다. 원인을 추측하지
않고 측정한 결과:

- 40일 구간 프로파일: 두 stage 동일(0.9초), 이상 없음
- 50일 단위 7구간: 전부 1~2초, 두 stage 배수 1.0~1.1×
- **전체 1회 직접 측정: 두 stage 모두 11.2초**

즉 커널은 느려지지 않았다. 원인은 `scripts/compare_v37.py` 가 **반복 결과를 리스트로
보관**한 것이다. 1회 결과가 `exposure_steps`+`lam`+`fallback` 약 9만 항목이라
20회(4 stage × 5회)를 들고 있으면 180만 항목이 되어 GC·메모리 압력으로 뒤 단계일수록
느려진다. 회차별로 즉시 집계하고 버리도록 고쳤고 **노출 수치는 그대로다.**

교훈: 반복 실행 러너(`scripts/run_experiment.py`, v4.0 Phase 1)도 같은 함정을 피해야
한다 — 원자료를 전부 메모리에 들고 있으면 안 된다.

## Part B. 체류 비율

`dwell_steps = horizon // 8`(12.5%) 를 `config.DWELL_RATIO` 로 꺼내고 기본값을
**0.75** 로 두었다. `run_project_workers(dwell_ratio=...)` 로 스윕 가능하다.

**0.75 에는 근거가 없다.** 2D 의 `DWELL_STEPS/WORKDAY_STEPS` (21,600/28,800) 를
가져온 것이며 그 2D 값도 실측·문헌값이 아니다.
`build/limitations.md` §2-B 에 민감도 최우선으로 등록했다.

### 파급 — **예측과 반대로 나왔다**

지시서는 "passage_count 가 줄고 dwell_time 이 크게 느는 것이 정상"이라고 했다.
실측은 그렇지 않다 (`hazard_zones.json` 의 `exposure_channel` 로 집계):

| 노출채널 | stage6 | stage7b | stage7c | s6→s7c |
|---|---|---|---|---|
| `dwell_time` (H001·H007) | 34,207 | 36,054 | 34,787 | **+1.7%** |
| `passage_count` (H002·H004·H009·H011) | 69,975 | 72,006 | 78,085 | **+11.6%** |
| `zone_occupancy` (H008) | 6,147 | 6,297 | 6,220 | +1.2% |

**체류를 6배 늘렸는데 dwell_time 은 1.7% 만 늘고 passage_count 가 11.6% 늘었다.**

원인으로 확인된 것:

1. **체류 지점이 위험 셀이 아닐 수 있다.** 작업자는 목표 셀 3×3 안에 머무는데,
   그 목표는 액티비티 요소(기둥·벽·슬래브)의 셀이지 위험구역 셀이 아니다.
   체류를 늘리면 **위험구역을 지나는 시간이 줄어드는 방향**도 함께 작동한다.
2. **stage7b→7c 의 증가분(passage_count +8.4%)은 대부분 `narrow` 채널이다**
   (21,231 → 28,072, +32%). 이는 Part C 의 ρ 표집 변경 때문으로 보인다 —
   `crews.json` 의 분포가 `mean/sd = null` 이라 이전에도 `uniform(0.15, 0.90)` 였고
   `social.init_rho` 도 같은 범위지만, **foreman(ρ=0.20 고정)이 새로 생겨** 크루당
   1명이 강한 회피자가 되었고 나머지 표집 순서가 바뀌었다. 시드 소비 순서가 달라져
   같은 분포라도 개별 값이 달라진다.

**이 두 번째 원인은 "확률적 변동을 늘렸다"가 아니라 "표집이 달라졌다"에 가깝다.**
stage7c 의 증가를 Part C 의 효과로 해석하면 안 된다. 분리하려면 foreman 배정만
켠 조건을 따로 돌려야 하며, **이번에 하지 않았다.**

전체 표는 `build/stage7_comparison.md` 참조.

### B-3 POI 순회 구조 — 현황만 조사했다 (구조 미변경)

전문은 `build/poi_structure.md` (`scripts/poi_structure.py` 산출). 요지:

| 물음 | 답 |
|---|---|
| 하루에 여러 액티비티를 순회하는가 | **아니다. 1명 = 1 액티비티 고정.** `make_workers` 가 crew_spec 단위로 만들고 `Worker4D.activity_id` 는 하루 동안 바뀌지 않는다. 순회하는 것은 그 액티비티의 **목표 셀(POI)** 이다. |
| 순서는 무엇이 정하는가 | **무작위.** `w.targets[rng.randrange(len(w.targets))]` — 방문 이력을 보지 않아 같은 셀을 연속으로 뽑을 수 있고 소진도 하지 않는다. 2D `_assign_task_queue` 의 `[4D 격리점]` 주석이 말한 "공정 스케줄에서 채우도록 교체" 는 **아직 안 되어 있다.** 공정이 정하는 것은 _그날 어느 액티비티가 활성인가_ 까지다. |
| 액티비티당 목표 셀 수 | 중앙값 476 (25%/75% = 55/1,213, 범위 1~1,925, 표본 71) |

체류 비율을 올린 뒤 하루 방문 POI 수:

| 단계 | 체류스텝 | POI/워커일 |
|---|---|---|
| stage6 | 10 | 1.41 |
| stage7b | 60 | 0.83 |
| stage7c | 60 | 0.86 |

**1 미만은 하루 안에 목표에 도달하지 못하고 끝나는 워커가 있다는 뜻이다**
(80스텝 × 2스텝당 1칸 = 하루 최대 40칸). 즉 방문 수를 지배하는 것은 체류 비율보다
**하루 스텝 수**다. 제안은 `build/poi_structure.md` §4 에 적었고 **이번에 바꾸지 않았다.**

## Part C. 확률적 변동

### 이식한 것

| 항목 | 방법 | 비고 |
|---|---|---|
| ρ 개인차 | `social.init_rho` **import** | `social.py` 미수정 |
| foreman | 크루(액티비티)당 첫 1명, `RHO_FOREMAN` 고정 | **배정 규칙에 근거 없음** |
| 출발 시각 분산 | `depart` 까지 `wait` 상태 | 2D `step_world` 와 같은 구조 |
| 체류시간 개인차 | `DWELL_JITTER_FRAC` ±편차, 평균 유지 | 2D 와 같은 방식 |
| 작업 중 미세이동 | `MILL_MOVE_PROB`, 목표점 3×3 안 | 2D 는 `zone_cells`(앵커 3×3) |
| 모방 | `social.apply_imitation` **import** | 아래 참조 |

**모방은 같은 층 안에서만 작동한다.** `run_level_day_workers` 에 넘어오는 workers 가
이미 한 층의 인원이기 때문이다. `social.apply_imitation` 은 `.pos/.rho/.is_foreman/
.injured` 를 읽고 `.rho` 만 쓰는데 `Worker4D` 에 `injured` 가 없어, `social.py` 를
고치지 않기 위해 `_ImitationProxy` 얕은 어댑터로 넘긴다.

**출발 시각 분산은 운용 horizon 에서 0 스텝이다.** 2D 비율(120초/28,800스텝 =
0.4167%)을 환산하면 80스텝에서 0.33 → 0 이 된다. **숫자를 올려 만들지 않았고**
그 사실을 여기 남긴다. horizon 을 키우면 자동으로 살아난다.

### 이식하지 않은 것과 사유

| 항목 | 사유 |
|---|---|
| **사고 표집** (`rng.random() < p`) | 4D 는 λ(기대건수) 방식이 옳다. 2D `run_one_day` 주석이 이미 정당화한다 — "확률이 1e-8 수준이라 사고를 표집하면 거의 0건이 나온다". 이식하면 4D 결과가 대부분 0 이 된다. |
| **`apply_witness_shock`** | **구조적으로 이식 불가.** 이 함수는 사고 발생 지점(r, c)을 받아 반경 내 ρ 를 낮춘다. 4D 에는 사고 개체가 없어 **발화 지점이 존재하지 않는다.** λ 임계값으로 대체 발화를 만드는 것은 2D 와 다른 메커니즘이라 별도 정당화가 필요하며, 이번에 만들지 않았다. |
| PPE 상태 | 2D 에서도 미사용 필드다. |

### 계수형 0.00% 는 잡음이 아니라 구조다

짝지은 비교에서 **모든 회차·모든 ρ 수준에서 차이가 정확히 0** 이다(±0.00).
AgentParameterRule 은 λ 배율만 부여하고 격자를 바꾸지 않으므로 작업자는 BASE 와
비트 단위로 같은 경로를 걷는다. 이것이 참값이며, 앞서 짝짓지 않은 판에서 보인
±0.4% 는 시드가 달라 생긴 가짜 변동이었다.

**파라미터를 조정해 신호를 만들지 않았다.**

### 통과하지 못한 부분에 무엇이 더 필요한가

계수형이 노출을 바꾸려면 **경로 가중 배율이 라이브러리에 있어야 한다.**
현재 `hazardWeightMultiplier` 는 전체 규칙 중 1건(`RULE_HS_DEBRISNET`)이고
그마저 `drop_zone` 이라 2D 셀타입 대응이 없다. 선택지는 §A-2 에 적은 둘뿐이며,
둘 다 **새 값 또는 새 모델링 결정**이라 별도 정당화가 필요하다.

다만 이것이 실험을 막지는 않는다 — 축 1 실험의 [S] 10건 중 **6건이 형상·시점형**
이고 그 6건은 +8~11% 의 유의한 저감을 낸다. 계수형 4건은 **λ 로만 비교**해야 하며
(노출이 아니라), 그 사실을 결과 해석에 명시해야 한다.
